# 0023. 核心重启语义：复用卸载/加载路径，无重启专有钩子

- Status: accepted
- Date: 2026-10-03

## Context

项目形态早已确立：常态更新只动插件（热更新）；核心自身更新走干净重启。待答的问题是插件侧是否需要配套的重启语义——核心重启时插件如何关、如何起。讨论见 `../design/fiber.md` §10。

被淘汰的选项：

- **重启专有钩子/语义**（插件可区分"为核心重启卸载"与"为热更新卸载"）：违背 fiber 单一清理契约哲学——同一笔 effect 不该因卸载原因有两种结清方式；增加插件作者心智负担而无收益
- **进程内核心热交换**（不重启进程替换核心）：运行时自身状态也须版本化迁移，复杂度失控，直接否决

## Decision

- **核心重启 = 进程级干净重启**；插件侧不引入任何重启专有语义，全程复用现有生命周期：
  - **关闭 = 全量 unload**：复用 drain 路径——LIFO 结账、优雅执行（disposer 可 await 在途持久化）、超时强制、依赖者先卸（[ADR-0018](0018-service-registry.md) S4 四段论原样适用）
  - **启动 = 全量 load**：复用启动路径——loader 挂载 entry + 激活门 + Pending 解析（与 [ADR-0018](0018-service-registry.md) "恢复路径 = 启动路径复用"同一条筋）
- 插件不区分"为核心重启卸载"与"为热更新卸载"——同一清理契约

## Consequences

- 派生登记（不决）：**跨重启状态政策**——进程死则 VM 全灭，什么状态落盘活下来（落盘 seam 原子写）、agent 自身连续性（进行中的对话、待审批）如何恢复，与 journal/replay 设计强耦合；**优雅关闭细则**——SIGTERM 处理、drain 总预算、in-flight 服务调用与邮箱残留处置，实现期议题
- 展开讨论与状态归属：`../design/fiber.md` §10
